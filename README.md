# 🏦 Bank System

> **Python과 Oracle Database를 활용한 콘솔 기반 은행 관리 시스템**

**Bank System**은 실제 은행 서비스에서 사용되는 주요 기능을 콘솔 환경에서 구현한 **개인 프로젝트**입니다.

회원가입과 로그인을 시작으로 계좌 생성, 계좌 조회, 입금·출금, 계좌이체, 거래내역 조회 및 관리자 기능까지 구현하여 **은행 서비스의 기본적인 데이터 흐름과 DB 처리 과정을 직접 설계하고 구현**했습니다.

특히 Oracle Database와 Python `oracledb`를 연동하고, 계좌이체 과정에서 **Commit / Rollback을 적용하여 데이터의 일관성을 유지하는 트랜잭션 처리**를 구현하는 데 중점을 두었습니다.

## 🎯 Project Goal

### "은행 업무를 코드로 구현하며 데이터의 흐름을 이해하다."

은행 시스템은 단순히 데이터를 저장하고 조회하는 프로그램이 아니라,

**회원 → 계좌 → 거래 → 거래내역**

으로 이어지는 데이터 관계와 함께

**입금 → 잔액 변경 → 거래 기록**

과 같은 여러 DB 작업을 하나의 업무 단위로 처리해야 합니다.

이 프로젝트에서는 이러한 실제 서비스의 흐름을 직접 구현하면서 다음을 학습하는 것을 목표로 했습니다.

* Python을 활용한 콘솔 애플리케이션 개발
* Oracle Database 연동
* SQL을 활용한 데이터 CRUD
* 사용자 인증 및 권한 관리
* 계좌 및 거래 데이터 설계
* 데이터 검증 및 예외 처리
* Transaction / Commit / Rollback
* 여러 테이블 간 JOIN 처리
* 기능별 Python 모듈 분리


실제 코드에서도 계좌번호 직접 입력 방식과 사용자 ID를 통한 계좌 검색 방식을 모두 지원합니다.

## 💳 계좌이체 처리

계좌이체는 하나의 업무 단위로 처리해야 하기 때문에 다음 작업을 하나의 Transaction으로 묶었습니다.

```text
┌──────────────────────────┐
│       계좌이체 시작       │
└────────────┬─────────────┘
             ↓
       출금 계좌 확인
             ↓
       잔액 확인
             ↓
       이체 금액 검증
             ↓
   ┌─────────┴─────────┐
   ↓                   ↓
출금 계좌             입금 계좌
BALANCE 감소          BALANCE 증가
   │                   │
   └─────────┬─────────┘
             ↓
      거래내역 INSERT
             ↓
          COMMIT
             ↓
        이체 완료
```

이체 과정에서 오류가 발생하면 `ROLLBACK`을 수행하여 부분적으로 데이터가 변경되는 상황을 방지하도록 구현했습니다.

### Transaction 처리

```python
try:
    출금 계좌 잔액 감소
    입금 계좌 잔액 증가
    거래내역 저장

    connection.commit()

except Exception:
    connection.rollback()
```

이를 통해 **출금은 되었지만 입금되지 않는 데이터 불일치 문제**를 방지하도록 구성했습니다.

# 🌐 다른 DB와의 계좌이체

일반적인 계좌이체뿐만 아니라 **다른 Database와 연결하여 계좌이체를 수행하는 기능**도 구현했습니다.

```text
Local Database
      │
      │ 계좌이체 요청
      ↓
Remote Database
      │
      │ 상대 계좌 확인
      ↓
   거래 처리
      │
      ↓
Transaction 기록
```

이를 통해 단일 데이터베이스 환경뿐만 아니라
**서로 다른 DB 환경에서 데이터를 주고받는 구조**를 경험했습니다.

# 📜 거래내역 조회

사용자가 보유한 모든 계좌의 거래내역을 통합하여 조회할 수 있습니다.

거래내역에는 다음 정보를 제공합니다.

* 거래일시
* 거래 유형
* 상대방 계좌
* 거래 금액
* 입금 / 출금 방향

```text
거래일시             유형       상대방/출처          금액
────────────────────────────────────────────────────
2026-08-20 10:30:21  입금       본인입금          +100,000원
2026-08-20 11:10:42  계좌이체   To: 123-456-789012  -30,000원
2026-08-20 12:05:13  계좌이체   From: 987-654-321012 +50,000원
2026-08-20 13:20:01  출금       본인출금          -20,000원
```

거래 유형에 따라 입금은 `+`, 출금은 `-`로 표시하고,
계좌이체의 경우 출금 계좌와 입금 계좌를 구분하여 표시하도록 구현했습니다.

# 🧩 핵심 구현

## 1. 계좌번호 자동 생성 및 중복 검증

계좌 생성 시 무작위 숫자를 조합하여 계좌번호를 생성하고,
기존 `ACCOUNTS` 테이블의 계좌번호와 비교하여 중복을 방지했습니다.

```text
계좌번호 생성
     ↓
기존 계좌번호 조회
     ↓
중복 여부 확인
     │
 ┌───┴───┐
 │       │
중복     사용 가능
 ↓           ↓
재생성     계좌 생성
```

---

## 2. DB Transaction 처리

계좌이체에서는 여러 SQL이 하나의 업무로 연결됩니다.

```text
UPDATE 출금 계좌
       ↓
UPDATE 입금 계좌
       ↓
INSERT 거래내역
       ↓
   ┌───┴────┐
   ↓        ↓
 성공      오류
   ↓        ↓
COMMIT   ROLLBACK
```

따라서 중간 단계에서 오류가 발생하더라도 전체 작업을 취소할 수 있도록 구현했습니다.

---

## 3. SQL JOIN을 활용한 데이터 조회

단순히 하나의 테이블만 조회하는 것이 아니라 사용자, 은행, 계좌 정보를 연결하여 실제 서비스에서 필요한 형태로 데이터를 조회하도록 구현했습니다.

```sql
SELECT
    A.ACCOUNT_NUM,
    B.BANK_NAME,
    A.BALANCE,
    A.ALIAS,
    U.USER_NAME
FROM ACCOUNTS A
JOIN BANKS B
    ON A.BANK_ID = B.BANK_ID
JOIN USERS U
    ON A.USER_ID = U.USER_ID
WHERE A.USER_ID = :1;
```

이를 통해 DB에 저장된 정규화된 데이터를 서비스에서 필요한 형태로 조합하는 과정을 경험했습니다.

# 🚧 Challenges & Improvements

## Transaction 처리

계좌이체는 단순히 한 계좌의 잔액만 변경하는 작업이 아니라,

**출금 계좌 잔액 감소 + 입금 계좌 잔액 증가 + 거래내역 저장**

이라는 여러 작업이 동시에 성공해야 하는 기능입니다.

따라서 일부 작업만 성공하는 상황을 방지하기 위해
Commit / Rollback을 활용하여 하나의 Transaction으로 처리했습니다.

## 데이터 검증

사용자가 직접 콘솔에서 데이터를 입력하기 때문에
잘못된 입력에 대한 검증이 중요했습니다.

예:

* 존재하지 않는 계좌번호
* 잔액보다 큰 금액의 출금
* 0원 이하의 이체 금액
* 최초 입금액 부족
* 존재하지 않는 사용자
* 중복 계좌번호

이러한 입력값을 DB에 전달하기 전에 검증하도록 구현했습니다. 계좌 생성에서는 최초 입금액을 1,000원 이상으로 제한하고, 계좌이체에서는 0원 이하의 금액과 잔액 초과 이체를 차단합니다.
